1Passwordを解約した理由は単純で、**年額の固定費が高い、もったいないと思ったからだ。** パスワードマネージャーは毎年黙って引き落とされる類の支出で、使い続けるほど総額が積み上がる。

やめるだけなら解約すればいい。移す先が見つかったのは、自分のサーバーについて調べていた時期だった。**自前サーバーの典型的な使い道としてパスワード金庫があると知り、それで興味を持った。** 写真や書類を自分の機械に置くのと同じ列に、パスワードも並んでいた。

ただ、パスワードを自分のサーバーに置くのは怖くないか、という話が残る。そこで**パスキー(WebAuthnという国際標準規格で実現されている、パスワードの代わりに指紋・顔認証などでログインする仕組み)を勉強した。** 仕組みを調べたうえで「これは安全な方法だ」と自信を持てたので、実行した。怖いけれど飛び込んだのではなく、勉強して安全だと納得してから動いた、という順番だ。

**この記事でやること** — 年額の固定費を理由に1Passwordを解約し、そこで管理していたパスワード15件・パスキー15件を自前サーバーで動かすVaultwardenへ移す。パスキーは仕組み上コピーできないので、サイトごとに手で登録し直す。手順は[ページ後半](#手順)にまとめた。

先に役割を書いておく。**コマンドと設定ファイルを書いたのはClaude（AnthropicのAIアシスタント）で、私は決める側をやった。** 構築の中身を考えなくていいぶん、「どのパスワードをどこに預けるか」という本題だけを考えられた。だからこのページも、前半に自分で決めたこと、後半に手順という形にしてある。

パスワード自体の移行はエクスポート・インポートで数分で終わる。時間がかかるのはパスキーの再登録で、仕組み上コピーができず、サイトごとに手作業で登録し直す必要があった。

---

## 決定1 — 年額の固定費を理由に1Passwordを解約した

**日付** 2026年9月12日

**迷ったこと** 1Password自体は不満なく動いていた。それでも払い続けるかどうか。

**採った案** **解約する。** 判断の根拠は料金だ。毎年かかる固定費に対して、自分が受け取っているものが釣り合っていないと考えた。製品の出来の話ではなく、支出の話として切った。

**却下した案** 払い続けて現状を維持する。

**なぜ却下したか** 移す先の見当がついた時点で、払い続ける理由が料金分だけ残り、その料金がもったいなかった。自分のサーバーについて調べているうちに、自前サーバーの典型的な使い道としてパスワード金庫があると知り、移せることが分かった。

**残った教訓** **毎年自動で引き落とされる支出は、不満がないぶん点検されない。** 不満の有無ではなく金額で一度数えると、判断が動く。

---

## 決定2 — パスキーを勉強して納得したうえで、自前に移した

**日付** 2026年9月12日

**迷ったこと** パスワードを自分のサーバーに置いて本当に大丈夫なのか。会社に預けておくほうが安全なのではないか。

**採った案** **パスキーの仕組みを先に勉強し、安全だと納得したうえで移した。** パスキーはWebAuthnという国際標準規格の上に乗っていて、秘密の側は手元から出ていかない設計になっている。そこを理解できたことが自信になり、移行に踏み切った。

**却下した案** 仕組みを分からないまま、とりあえず移してみる。

**なぜ却下したか** パスワード金庫は失敗したときの損害が大きい領域だ。分からないまま動かして後から学ぶ順番だと、学ぶ前に取り返しのつかない形を作ってしまう。

**残った教訓** **順番が結論の質を決める。** 「怖いけどやる」ではなく「勉強して納得してからやる」にすると、途中で出てくる不安が勘ではなく仕組みの話として処理できる。

---

## 決定3 — パスキーを全部Vaultwardenに寄せなかった

**日付** 2026年9月12日

**迷ったこと** 1Passwordを棚卸しして出てきたパスキー全15件を、どこに登録し直すか。

**採った案** **用途によって使い分ける。** **ブラウザの拡張機能を自由に入れられない端末から使うアカウント**は、拡張機能のインストールが要らずQRコードでのクロスデバイス認証(手元のスマートフォンで認証を代行する方式)に対応しているiCloud Keychainへ。それ以外の、データ主権の方針に寄せたいアカウントは、パスワードと同じ場所で一元管理できるVaultwardenへ。

**却下した案** 全件をVaultwardenに一本化する。

**なぜ却下したか** 拡張機能を自由に入れられない端末が手元にある。そこで使うアカウントまでVaultwardenに寄せると、いざ使う場面でログインできない。

**残った教訓** **「全部を1箇所に」はそれ自体が目的ではない。** 使う場面ごとに成立する置き場所を選ぶほうが、一元管理の見た目の美しさより実用に効く。

# 手順

ここから下は**Claudeが書き、自分の環境で実行して結果を確かめたもの**だ。2026年9月の版で、実際にこれでパスワード15件・パスキー15件が移った。

置いておく理由は2つある。ひとつは、**作業の全体像と長さが先に分かる**こと。見てのとおり5段階で、サーバー側は半日もかからない。時間を食うのはパスキーの再登録だけだ。もうひとつは、**自分が使っているAIに「これと同じことをやりたい」と渡す材料になる**こと。ゼロから説明するより、動いた実例を見せたほうが早い。版が新しくなっていれば、そのとき合った形に直してくれる。

## 移行先の比較 — Claudeが提案した選択肢

自前ホストのパスワードマネージャーには複数の選択肢がある。**どれを比べるべきかの整理と比較はClaudeが提案したもの**で、以下はその内容だ。

- **Vaultwarden** — Bitwardenというサービスの非公式互換サーバー実装。公式のBitwardenアプリ・ブラウザ拡張機能がそのまま使え、UIの完成度も高い。ゼロ知識暗号化(サーバー側もマスターパスワードを知らない設計)。普段使っているNextcloud・Immichと同じサーバー上に同居させられる。
- **KeePassXC** — サーバーを立てず、暗号化されたファイル1つで管理するタイプ。オフラインで完結するが、複数端末間の同期を自分で用意する必要がある(クラウドストレージと組み合わせるのが一般的)。
- **Bitwarden公式のクラウド版** — セルフホストではなく、Bitwarden社のサーバーに預ける形。

この整理を見て、公式クラウド版は1Passwordと似た構図になる(預け先の会社が変わるだけになる)ため外し、公式アプリがそのまま使える点と既存サーバーに同居できる点からVaultwardenを採った。

## 前提

以下がすでに用意できていることを前提にする。まだの場合は先に[自分の「サーバー」を持つとはどういうことか](/ja/notes/self-hosting-basics/)を読んでほしい。

- 常時起動しているLinux環境(Docker Engineが使える状態)
- 自分名義のドメイン、Cloudflare Tunnelが動いている状態(導入手順は[前々回の記事](/ja/notes/google-drive-to-nextcloud/)のStep 3と同じ)

## Step 1: docker-compose(複数のコンテナをまとめて定義・起動するDockerの仕組み)でVaultwardenを構築する

Vaultwardenは公式イメージを使えばコンテナ1つで完結し、Nextcloudのようにデータベースを別途用意する必要もない分、今回の中では一番シンプルな部類だった。

```bash
mkdir ~/vaultwarden && cd ~/vaultwarden
```

`docker-compose.yml`:

```yaml
services:
  vaultwarden:
    image: vaultwarden/server:latest
    restart: always
    environment:
      - DOMAIN=https://vault.example.com
      - ADMIN_TOKEN=<自分で決めた長いランダム文字列>
      - SIGNUPS_ALLOWED=false
    volumes:
      - ./vw-data:/data
    ports:
      - 127.0.0.1:8082:80
```

いくつか説明が要る項目がある。

- `DOMAIN` — 最終的に外部からアクセスする本物のURL(自分のドメイン)を指定する。ここがずれているとパスキー(WebAuthn)登録時にエラーになることがある。
- `ADMIN_TOKEN` — サーバーの管理画面(`/admin`)に入るための鍵。長いランダム文字列にし、他の誰にも教えない。
- `SIGNUPS_ALLOWED=false` — 新規アカウント登録を締め切る設定。自分専用サーバーなので、自分のアカウントを最初に1つ作ったらこれをオフにして、他人が勝手にアカウントを作れないようにする。

起動する。

```bash
docker compose up -d
docker compose ps
```

`http://localhost:8082`にアクセスし、「Create Account」から自分のアカウントを作成する。作成が終わったら`docker-compose.yml`を編集して`SIGNUPS_ALLOWED=false`に変更し、`docker compose up -d`で反映しておく。

## Step 2: Cloudflare Tunnelで公開する

Nextcloudの時([前の記事](/ja/notes/google-drive-to-nextcloud/))と同じ要領で、`/etc/cloudflared/config.yml`にVaultwarden用の行を追記する。

```yaml
ingress:
  - hostname: vault.example.com
    service: http://localhost:8082
  # ...他のサービスの行がここに続く...
  - service: http_status:404
```

編集後は`cloudflared tunnel ingress validate`で文法チェックしてから`sudo systemctl restart cloudflared`。DNS側もCloudflareの管理画面で`vault`のCNAMEレコードを`<トンネルID>.cfargotunnel.com`に向けておく。

## Step 3: ブラウザ・スマホから接続する

ブラウザはChrome・Firefoxの両方にBitwarden拡張機能を追加し、接続先の設定(拡張機能アイコン → 設定 → Self-hosted environment)に自分の`vault.example.com`を入力する。スマートフォン用の公式Bitwardenアプリも同様に接続先を変更するだけで使える。

パスワード自体の移行は、1Password側でエクスポートしたデータ(CSV形式など)をVaultwardenの「Import data」機能でインポートするだけで数分で終わった。ここは特につまづくところがなかった。

## Step 4: パスキーの移行

パスワードと違い、パスキー(WebAuthn)はエクスポート・インポートで移せない仕様になっている。サイトごとに「旧パスキーを削除 → 新しいマネージャーで再登録」という地道な作業が必要だった。どのパスキーをVaultwardenに寄せ、どれをiCloud Keychainに残したかの基準は決定3のとおり。

作業中に見つかった落とし穴:

- **ブラウザ拡張機能の競合**: 1Password拡張機能を有効にしたままだと、WebAuthnのリクエストを1Password側が横取りしてしまい、Bitwarden/Vaultwarden拡張機能が反応できない。`chrome://extensions`で1Password拡張機能を完全にOFFにする必要があった。
- **スマホ側の割り込み**: モバイル版Bitwardenアプリでパスキーを新規登録する際、Touch ID/Face IDのようなOS標準の認証より先にBitwarden拡張機能側が割り込んでしまい、登録に失敗することがあった。
- **iCloud Keychainを使う場合の見落としがちな設定**: macOSでiCloudキーチェーン経由のパスキー登録をするには、システム設定 → 一般 → AutoFill & Passwords の「Passwords」トグルが事前にONになっている必要がある(初期状態はOFF)。
- **削除する前に、実際に使っているか確認する**: 「もう使っていないはず」と思っていたサービスのパスキーが、実は現役で使われていると後から判明した件があった。一覧だけを見て「使っていなさそう」で判断せず、実際に使う場面があるかを確認してから削除する方が安全だった。

## Step 5: バックアップを設定する

Nextcloud・Immichと同じく`rclone`でBackblaze B2へ日次バックアップする。Vaultwardenの場合はデータベース(SQLite、1ファイルにまとまった軽量なデータベース形式)がそのままフォルダの中に入っているので、フォルダごと同期するだけでよい。

```bash
sudo rclone --config /home/<user>/.config/rclone/rclone.conf sync \
  ~/vaultwarden/vw-data "$B2_REMOTE/vaultwarden"
```

ここで**Claudeが提案した**のが、バックアップの取り出し鍵の置き場所だ。バックアップ自体はフォルダを同期するだけで済むが、同期先に接続するための鍵(`rclone`の設定ファイル`~/.config/rclone/rclone.conf`)はサーバー本体にしかない。サーバーが完全に壊れた時、バックアップを取り出す鍵ごと失われる「鶏と卵」の形になっている。

対処は、この設定ファイルの中身をVaultwarden自身にSecure Note(パスワード以外のメモも安全に保存できる機能)として複製保存しておくことだった。Vaultwardenはクライアントアプリに一度ログインしておけばオフラインキャッシュが残るため、サーバーが全損してもスマホから鍵を取り出せる。何もしなければ鍵はサーバー本体にだけ残り、全損時にバックアップと鍵を同時に失う。**バックアップの有無だけを見ていると、この一段上の依存関係を見落とす。**

このバックアップ自体を「乗っ取られても消されない」形にする話は[バックアップを「消されても戻せる」形にする](/ja/notes/backup-ransomware-resistant/)に別途書いた。

## 結果

パスワード15件・パスキー15件、全て移行完了。1Passwordは解約し、年間の固定費を1本減らせた。これが元々の目的だった。パスワードの移行自体は簡単だが、パスキーは仕組み上コピーできないので、サイトごとの再登録作業を見込んでおくとよい。
