今の構成を一から立てるなら、どの順でやるか。写真・ファイル・パスワード・予定表・そして自分のドメインのメールを、借りたサーバー1台に載せるまでの順序だ。1か月の作業を時系列で並べたものではない。判断と日付、そしてこの順序のどこで何に刺されたかは[1か月の判断記録](/ja/writing/self-hosted-server-decisions/)にある。

コードは書かない。ここから下はClaude（AnthropicのAIアシスタント）が書き、自分の環境で実行して結果を確かめたものだ。置いておく理由は2つある。**(1) 着手する前に作業の全体像と長さが分かる。(2) 読者が自分のAIに「これと同じことをやりたい」と渡す材料になる。**

**このページは日付つきの記録で、保守し続ける手順書ではない。** コマンドは2026年9月〜10月時点で動いたものだ。残るつもりで書いているのは考え方のほうで、価格・版番号・事業者の設定画面の文言は残らない側だ。各ソフトの現在の書式は公式ドキュメントで確認してほしい。

## 前提の環境

- 借りたサーバー1台(Ubuntu 24.04)。2026年9月時点で6vCPU / 12GB RAM / 200GB SSD / 転送量無制限が月$9.00、初期費用ゼロ、1ヶ月契約
- Docker Engineと`docker compose`が使える状態
- 自分が持っているドメイン1つ
- 別会社のオブジェクトストレージ1つ(自分はBackblaze B2)。**サーバーと同じ会社にしない**
- 手元に、そのサーバーとは別のパソコンが1台。**ファイアウォールの検証はこれが無いと原理的にできない**(Step 2)

## Step 1: サーバーとドメインを決める

**プランはメモリとディスクで決まる。** ディスクはデータ実測の1.2〜1.5倍。自分は写真115GB＋ファイル16.6GBに対して、OS・Docker・データベース込みで170〜180GBと見積もって200GBから始めた。

**メモリは写真の量ではなくコンテナの数で決まる。** ここは一度間違えかけた。「古い写真を外へ逃がすならメモリも小さくていい」と考えたが違う。自分は常時14コンテナで、以前メモリ不足で全サービスが繰り返し落ちた実績がある。しかも**借りたサーバーにGPUは無いので、顔認識や画像検索をCPUとメモリでやることになり、必要メモリはむしろ増える。** 下げるのは安定を確認してからでいい。

**リージョンは「近いほう」では決まらない。** 自分の場合、第一候補のリージョンは追加料金がつく上に在庫切れだった。追加料金ゼロのリージョンに変えたら、結果として**バックアップ先との経路が短くなり、復元も日次バックアップも速くなる**という副産物があった。申込画面に出る遅延の数字は**生のネットワーク遅延で、トンネル経由の実構成には当てはまらない。**

**年契約の割引は見送った。** 移行先が気に入らなかったときにすぐ降りられないのは本末転倒だから。

**ドメインは自分で取り、メールの配信は業者に任せる。** これが最初の1か月で一番効いた。アドレスが自分のものなので、業者を替えても誰にも「アドレスが変わりました」と言わなくて済む。配信まで自前にしない理由は決定2に書いた。

## Step 2: 外からポートを開けずに公開する

**ルーターやファイアウォールに穴を開ける方式をやめ、サーバー側から外へ繋ぎに行くトンネルを使う。** 自分はCloudflare Tunnelを使っている。入口が1本に絞られ、サーバーのアドレスも外に出ない。

その上で、**コンテナは最初からループバックに縛る。**

```yaml
ports:
  - '2283:2283'            # 🔴 これは全てのネットワークに向けて開く
  - '127.0.0.1:2283:2283'  # ✅ 自分自身からしか届かない
```

トンネルの常駐プロセスはサーバー上で動いて`localhost`を叩くので、ループバックに縛っても公開には影響しない。**自宅のルーターの内側では両方とも同じ結果になるが、公開アドレスを持つサーバーでは全く違う。** 自分の守りはファイアウォールではなくこの設計に依存させている。1行消えれば無防備に戻るファイアウォールより、そもそも誰も外向きに待ち受けていない状態のほうが強い。

棚卸しは**除外方式**で書く。

```bash
# 🔴 これでは漏れる
ss -tlnp | grep 0.0.0.0

# ✅ 「自分自身以外」を除外方式で全部出す
ss -tlnp | grep -vE "127\.0\.0\.|\[::1\]"
```

`*:PORT`(IPv4とIPv6の両方で待ち受け)という表記は`0.0.0.0`では引っかからない。自分は認証なしのポート19本をこの形で見落とした。**ホスト上で直接動いているプロセスはDocker向けのファイアウォール設定では止まらない**ので、コンテナだけ見ていても足りない。**IPv4を塞いだら必ずIPv6も確認する。** 設定は完全に別物だ。

検証は**必ず別のパソコンから**やる。

```bash
nc -vz <サーバーのアドレス> 2283   # → Operation timed out  が正しい
nc -vz <サーバーのアドレス> 22     # → succeeded!            が正しい
nc -vz -6 <IPv6アドレス> 2283      # IPv6も必ず測る
```

サーバーの中から自分の公開アドレスに繋ぐと内部の経路を通るので、**塞がっているのに必ず「繋がる」と出る。** これを再起動後・ファイアウォールを触った後・コンテナの設定を触った後に回す定型チェックとして文書にしておく。

## Step 3: サービスを1本ずつ足す

まとめて足さない。1本動かすたびに、トンネルの経路・バックアップの対象・監視の対象に3点セットで登録してから次へ行く。**後から足した分がどれか1つに入っていない**のが、あとで一番高くつく。

自分が今動かしているのは、写真・ファイル・パスワード・予定表と連絡先・ログインの入口・ソースコードの保管庫・死活監視・自分用のチャットとカレンダーのアプリ。

**HTTP 200は動作証明ではない。** 切替後に200を返しながら中身が動いていなかったことがある。**切替前に、そのサービスで実際に1往復させる実機検証を入れる。** 利用者が自分以外にもいるなら、ここを飛ばしてはいけない。

## Step 4: ログインの入口を1つにする

各サービスに別々のパスワードを置くのをやめ、入口をひとつにまとめる仕組み(自分はAuthentik)を前に置く。

ここで実際に踏んだ穴を2つ。

🔴 **パスワード段を外すときは、多要素の段の「未設定のときどうするか」をセットで見る。** 自分の設定は多要素の段が`skip`だったので、**認証器を1つも持たないユーザーはユーザー名だけでログインできる**状態になりかけた。`deny`に変える。

🔴 **入口を一本化しても、各アプリ独自のログイン扉は別に閉まらない。** 入口側をパスキーに寄せても、アプリ自身が持っている素のログイン画面は生きている。1本ずつ無効化するか、前段で遮断する必要がある。

**退路を2つ以上残す。** 自分はブラウザから入れる経路を作ったが、それは入口サーバーの認証を通る作りなので、**入口が閉じると使えない**(循環する)。退路は入口を経由しないものにする。自分の場合は手元のPCからの直接のSSHと、業者のコンソール経由の画面だ。予備の認証手段のバックアップコードは、パスワード管理サーバーが落ちたときのために**別の場所にも1部持つ。**

## Step 5: バックアップを「工程ごとに成否を言う」形で作る

ここが一番書き直した場所だ。

**スクリプトは工程ごとに`OK`/`FAIL`を出し、最後に完走マーカーを出す。** `set -e`で途中で止まる作りだと、何がどこまで終わったのか誰にも分からない。自分の旧スクリプトは**34回の起動中5回しか完走していなかった**(最終段がパスワード要求で止まっていた)。**完走マーカーが1ヶ月出ていないのに誰も気づかない**状態だったので、本当の失敗も検知できない。

⭐ **「分母」を点検する。** 「33件すべて成功」は「やると決めた33件は全部通った」としか言っていない。**スクリプトに書き忘れたサービスは永久に静かに落ちる。** ログでは絶対に分からない。点検は3方向から同時に見る。

```bash
docker ps                      # コンテナ
systemctl list-units --type=service   # systemdで動いているもの
ls /home/<user>                # データ置き場
```

**片方からだけ見ると、もう片方は構造的に見えない。** 自分の穴はここだった。アプリの本体の一部がDockerではなくsystemdで動いていたので`docker ps`には出ず、結果として**systemdのユニット定義・`crontab`・ファイアウォールのルールが1つもバックアップに入っていなかった**。データは全部戻るのに「どう起動するか」が戻らない状態だ。

📌 **`rclone`はシンボリックリンクを黙ってスキップする。** `/etc/systemd/system`は半分がシンボリックリンクなので、`cp -aL`で実体化してから渡す。踏むと「同期した気になって実は空」になる。

この点検は月1回の自動実行にして、**対象から漏れているものが出たときだけ**報告させている。

## Step 6: 復元の鍵をサーバーの外に置く

**復元はサーバー側が保管先から引っ張ってくる方式にする。** 押し込む方式だと、押し込む側の機械が生きている必要がある。サーバーが死んだときに復元したいのに、生きている前提の機械が1台要るのは変だ。これは決定4に書いた。

そして**その引っ張るための鍵と設定を、サーバーの外へ複製する。** 自分はパスワード管理サーバーのSecure Noteに4件入れている。

1. オブジェクトストレージのアクセス鍵を含む`rclone`の設定
2. トンネルの設定と資格情報
3. `docker-compose.yml`一式
4. 環境変数ファイルとsystemdのユニット定義

パスワード管理のモバイルアプリは一度ログインすればオフラインキャッシュを持つので、サーバーに一切アクセスできなくてもスマートフォンから取り出せる。**保存しただけで終わりにしない。** 「このメモの値だけで保管先の全データが見えるか」を別の端末で実測する。自分はこれをスクリプトにして、**鍵を入れ替えるたびに毎回回している。**

**復元テストを1回やる。** 自分は保管先の生ファイルから記憶用のディレクトリを復元し、124ファイルが`diff -rq`で完全一致することを確認した。**復元したことのないバックアップは、バックアップではない。**

## Step 7: バックアップを消されない形にする

サーバーが取られたときにバックアップまで消されるなら、オフサイトにした意味が半分になる。

**① サーバー上の鍵の権限を、実際に使う分まで絞る。** 自分の鍵は18権限を持っていて、**ライフサイクルの改変による即時削除も、複製ルールの停止もできた。** 「30日のバージョン保持があるから安全」は成立していなかった。スクリプトが実際に使うのは一覧・読み・書き・削除の5つだけだった。**Web管理画面の鍵発行UIでは権限を細かく選べない**ので、業者のCLIが必須になる。マスター鍵を扱う作業なのでサーバー上ではなく手元のPCから実行する。

**② 削除が伝播しない複製先を作る。** 自分が使っている業者の複製機能は**削除と論理削除の印を複製しない**仕様なので、複製先が構造的に追記専用のミラーになる。サーバー上の鍵が元のバケットに限定されていれば、複製先には構造的に届かない。

**①と②はセットで、順序は①が先。** ①をやらないと、②の複製ルールをサーバー側から止められてしまう。

**複製先のライフサイクルの設定で2つ間違えやすい。** 「最新版のみ保持」を選んではいけない(上書き攻撃の瞬間に正常な旧版が消え、複製先を用意した意味が消える)。「アップロードから何日で隠すか」の欄は空にする(数字を入れると現役のバックアップ本体が自動削除される)。埋めるのは「隠してから何日で削除するか」の1箇所だけだ。自分は毎晩上書きされるデータベースのダンプが**年80GB積み上がる**ので180日にした。

**鍵を入れ替えたら、旧鍵が本当に死んだかを実測する。** 自分は差し替えスクリプトの中に、読み・書き・削除の全テストに通ってからでなければ設定ファイルを書かない作りを入れた。

🔴 **ここで一度壊した。** 差し替えスクリプトが設定ファイルを「作り直す」作りだったため、後から足した暗号化用の設定が消え、直後のバックアップで5工程が全滅した。**構成に新しい設定を足したら、それを書き換える既存のスクリプトを洗い出す。** 「鍵の差し替え」という名前から、設定ファイル全体を作り直しているとは読み取れなかった。

## Step 8: 監視をサーバーの外に置く

死活監視をそのサーバーの上で動かすと、**サーバーごと落ちたら監視も一緒に落ちて通知が飛ばない。一番知りたい障害だけ通報されない。**

二段にする。サーバー上の監視は1分間隔で速いほうを、**サーバーの外で動く監視は遅くてもいいから絶対に黙らないほう**を担当させる。自分は後者をGitHub Actions(GitHubが決めた時刻にスクリプトを自動実行する仕組み)で30分間隔にした。

判定の設計で効いたこと。

- **4xxは「生存」扱いにする。** ログインが必要なサービスは未認証だと302や401を返すのが正常で、これを異常にすると常時誤報になる。異常とみなすのは5xxと、接続不能・時間切れだけ
- **3回連続で失敗して初めて異常とみなす。** 回線の瞬断で鳴らないための緩衝。既定が「1回失敗で即異常」になっている監視ソフトは、そこを揃える
- **通報は状態が変わった瞬間だけ。** 落ちている間ずっと鳴り続けない。復旧時は停止していた時間を添える。全部が同時に落ちたときは「サーバーごと落ちている可能性が高い」と文面を変える

🔴 **外部の定時実行には落とし穴がある。** GitHubは**リポジトリに60日間活動がないとスケジュール実行を自動停止する。** 異常が無いとコミットも発生しないので、**無事な期間が続くと監視が黙って止まる。** 変化がなくても7日ごとに観測値を更新してコミットを発生させる。あわせて、**定時実行は大幅に遅れる**(自分の実測で5時間超)ので、時刻を当てにした説明は書かないこと。価値は速さではなく黙らないことだ。

## Step 9: 容量が足りなくなったら、まず単に増やす

決定1のとおり、**最初に見るのは契約している業者の増設ボタン**だ。再インストールなし、移行なし、新しい部品ゼロ。比較表に載っていない退屈な案を1つ探す。

実務で知っておくこと。

- 増えた分は**既存ディスクの拡大として現れる**(別のディスクが増えるのではない)。ただし**パーティションとファイルシステムは自動では広がらない**
- 自分の環境では`growpart`と`resize2fs`の2コマンドで無停止のオンライン拡張ができた。これは「拡大したいパーティションが最後にあり、直後に連続した空き領域がある」ことが前提なので、**先に`--dry-run`で確認する**
- **ルートのパーティションテーブルを書き換える操作**なので、直前にバックアップを手動実行して全工程`OK`を確認するのが必須の作法
- ⚠️ **公式ヘルプに「再起動不要」と書かれていても、実際には強制リセットが起きた。** 増設系の作業はダウンタイムを見込む

単価で見ると、ディスク増設は**一番高い**選択肢だ。自分の規模では差額が月数ドルで、「その数ドルで複雑さを回避する」が正しかった。**規模が変われば答えは裏返る**ので、オフロードしたい古いデータが1TBを超えたら方式を見直す、という目安を書いておいた。

## Step 10: 「成功」の主張を外から検証できる形にする

最後に、決定3と決定5で残った型を道具にする。

**公開物や成果物に、それがどのソースから作られたかを書き込む。** 自分はサイトの公開物のルートに、ソースのコミットID・ビルドした時刻・参照を書いたファイル(`build-id.txt`)を置いた。本番のそれとソースの最新を比べれば、「公開が遅れている」のか「中身が落ちている」のかが切り分けられる。この2つは対処が正反対で、片方だと思って待っていると何時間も溶ける。**原因の特定はいらない。切り分けさえできればいい。**

🔴 **切り分けに使う目印は「毎回必ず変わるもの」にする。** 自分は一度、本番とソースで**直近の公開で中身が変わっていなかったファイル**をバイト比較して「配信は健全」と判定した。配信が凍っていても一致するので、**失敗しようのないテスト**だった。

同じ型をデータの検証にも当てる。**復元やコピーの検証を「件数の一致」でやってはいけない。** 自分の数字は60,525件と60,619件で0.15%差。見逃す水準だった。**データベースに記録されているパスが1件ずつ実在するか**を全件突き合わせる。合計の照合は、打ち消し合う誤りを隠す。

そして**確認は、作業したのと別の経路でやる。** 同じ経路で確認すると、同じ思い込みを2回通るだけになる。
