自分のサーバーに写真・パスワード・ファイルを集めたあと、バックアップを**2系統**持っていた。GitHubの非公開リポジトリ(自分だけが見られるGitの保管場所)への日次バックアップと、クラウドのオブジェクトストレージ(Backblaze B2)への日次バックアップ。多いほうが安全だと思っていた。

**この記事でやること** — 2系統あったバックアップのうちGitHubの非公開リポジトリ側を廃止し、クラウドのオブジェクトストレージ1系統に絞る。止める前に「止める側にしか無いもの」を1件ずつ突き合わせ、Gitの履歴は1ファイルに固めて逃がし、最後に実際に復元して突き合わせるところまでやる。手順は[ページ後半](#手順)にまとめた。

調べたら、どちらも完全ではなく、どちらも検証されていなかった。GitHub側を廃止して1系統に絞り、代わりに「本当に戻せるか」を確かめる作業を足した。

## 前提

- 常時起動しているLinuxサーバー1台に、パスワード管理・写真・ファイル置き場・認証を同居させた状態。土台は[自分の「サーバー」を持つとはどういうことか](/ja/writing/self-hosting-basics/)
- 道具は`rclone`(いろいろなクラウドストレージへファイルを同期するコマンド)。送り先はBackblaze B2(安価なオブジェクトストレージ。1GBあたり月$0.006、最初の10GBは無料)
- もう1系統は、作業用ディレクトリ一式を毎日`git commit`して非公開リポジトリへ`push`する自作の仕組み

## 2系統が実際に守っていたもの

同じものを2箇所に置いているつもりだったが、並べたら役割が違っていた。GitHub側はテキスト類(会話ログ・設定・メモ)と添付ファイルで、強みは**履歴**——「このファイルは3週間前どう書かれていたか」を追える。B2側はデータベースのダンプ・写真ライブラリ・ファイル置き場の実データ・パスワードの保管庫で、強みは**容量**。つまり二重化ではなく**分担**で、片方だけでは静かに欠けが出る状態だった。

実際に測ったら、添付ファイルが**B2に638件、GitHubに460件、重複ゼロ**。時期で真っ二つに割れていた。`git clone`だけで戻せば638件が消え、B2だけで戻せば460件が消える。

## 「2倍安全」ではなく「壊れたら困るものが2つ」

分担になっていた理由は単純で、**2つあると、どちらも真剣に見なくなる**。

B2側の同期スクリプトのログを読んだら、**34回の起動のうち完走は5回だけ**だった。最後の処理で`sudo`がパスワードを求めて止まり、`set -e`(途中で失敗したらそこで中断する設定)で全体が終わっていた。データ本体の各工程は成功していたので実害はなかったが、問題はそこではない。**「完走しました」のマーカーが1ヶ月出ていないのに、気づいていなかった。**

これが冗長なバックアップ経路の本当のコストだと思う。ディスク代でもなく手間でもなく、**どちらも検証されないこと**。「もう片方があるから」と思っている限り、片方が壊れても痛みが出ないので、気づく機会そのものが無くなる。

## GitHubがこの用途に向いていなかった理由

1. **サイズと中身**。Gitはテキストには強いが、**画像のようなバイナリは版が増えるたびに丸ごと溜まる**。`.git`(履歴の実体)が346MBあり、作業用ディレクトリ751MBの半分近くを占めていた(1年後には847MB)
2. **履歴は消せない**。消さないことが価値の仕組みなので、間違って入れたものが残る。実際、秘密情報を含むディレクトリ(APIトークン類やサーバーの秘密鍵)が**気づかないうちに毎日pushされ続けていた**。「除外設定に入れてある」と自分のメモに書いてあったが、入っていなかった
3. **他人のアカウント方針の上に乗っている**。容量制限も規約も将来どう変わるかは自分では決められない
4. **そもそも用途が違った**。置いていたのは日々の記録で、ソースコードではない。全ての版を永久に取っておく必要がない

一方で**「履歴が追える」価値は本物だった**ので代わりを用意した。B2の**バージョン保持**(上書き・削除された古い版を一定期間取っておく設定)で、自分のバケット(ストレージ上のフォルダのような入れ物)は旧バージョンを30日保持している。実際にデータベースのダンプは26世代遡れた。30日の「取り消し」が成立していればGitの履歴機能の大部分は代替できる。なお**公開しているもの(ブログ・ポートフォリオ)はGitHubのままにしている**。廃止したのは「バックアップ置き場として使うこと」だけ。

## 一本化の本体は棚卸しだった

ここが一番再利用できる部分だと思う。片方を止める作業の本体は、**「GitHub側にしか無いものが、B2側に全部入っているか」を1件ずつ確認すること**。やらずに止めると、欠けたことに気づくのは復元が必要になった日になる。

**1. 止める側の中身を、実物から列挙する**

設計書ではなく実際のファイル一覧から出す。自分はここで一度間違えた。手元のメモの箇条書きだけを読んで「テキスト類がB2に入っていない」と誤判断したが、スクリプト本文を開いたら既に実装済みだった。**メモで判断せず、スクリプト本文とファイル一覧を実見する。**

**2. 残す側の対象リストと突き合わせる**

ここで**本物の穴が見つかった**。環境変数をまとめたファイル(`.env`。各種サービスのトークンが入っている)が、**GitHubにもB2にも無かった**。2系統あったのに、どちらにも無いものが存在した。

**3. Gitの履歴そのものを、ファイルとして退避する**

履歴は普通のファイル同期では運べない。`git bundle`(リポジトリ全体を1ファイルに固める機能)を使った。

```bash
git bundle create /tmp/history-20260928.bundle --all
git bundle verify /tmp/history-20260928.bundle
rclone copy /tmp/history-20260928.bundle <暗号化remote>:<保存先>/
```

- 🔴 **`root`で`git`を叩くと`detected dubious ownership`で弾かれる**。ディレクトリの所有者ユーザーで実行する
- 出来上がりは831MB。**往復まで確認した**——取り出してmd5(内容の指紋)が一致し、`git clone <bundleファイル> <ディレクトリ>`で162コミットが復元でき、履歴の中にしか無いPDFを元のサイズどおり取り出せた
- 🔴 **一度きりのスナップショット**。以後履歴が伸びても自動では更新されない

**4. 止める前に「止める側にしか無いコミット」がゼロだと確認する**

`git rev-list --count <リモート>/main --not --all`が`0`であること。

**5. 浮いた分を別の軸に回す**

**テキスト類だけを対象にした軽い同期を1日4回**動かすようにした(全体の同期は従来どおり夜1回)。これでRPO(障害時に失われる最大の時間幅)が**最大24時間から最大6時間**に縮んだ。重い写真ライブラリに触らないので約10秒で完走する。加えて30日を超える長期の記録として、**テキスト類のみの日付付き`tar.gz`スナップショットを週1回**置いた。実測16MBなので年0.8GB、費用はほぼゼロ。

- 🔴 **バックアップを取る道具自体がバックアップ対象外だった**。同期スクリプトを置いたディレクトリは、どちらの系統にも入っていなかった。サーバーが全損したらデータは戻るが**戻し方を書いた道具が無い**
- 🔴 **データベースのダンプを取る行に管理者パスワードが直書きされていた**。**権限600の`.env`に切り出して読み込む**形にし、読めなければ`exit 1`、変数が空なら`: "${VAR:?未設定}"`で止める(黙って空のパスワードで走らせないため)。渡し方は`-p'…'`のような引数ではなく環境変数経由にする——引数は`ps`で他のユーザーから見える。なお**平文の秘密はスクリプト本文を直しても消えない**。過去の退避ファイルと稼働中のコンテナの環境変数に同じ値が残っており、本当に消すにはパスワードの変更が必要だった

## 何を金庫に入れるか

**バックアップを復元するための鍵が、バックアップの中にしか無いと、永久に開かない。** いわゆるブートストラップ問題(起動するために起動済みの何かが必要になる循環)。自分の場合、B2から取り出すための接続情報(`rclone`の設定ファイル)はサーバーの中だけにあった。毎日バックアップは成功していたが、**サーバーが丸ごと壊れた瞬間に、無事なデータを開ける人が誰もいなくなる**。

> **再発行できる鍵は金庫に入れない。再発行できない鍵だけ入れる。**

- **入れる(再発行不能)**: 暗号化パスワード(失うとバックアップが永久に読めない石になる)、ストレージ事業者のアカウントの2段階認証バックアップコード、復元用の接続情報
- **入れない(再発行可能)**: 各種APIトークン、ストレージのアプリケーションキー。上位のアカウントにログインできれば1分で作り直せる
- **置くべきは鍵そのものではなく、上位の認証**(アカウントのログイン情報と2段階認証)。それがあれば下位の鍵は何度でも生やせる
- 🔴 **何でも放り込むと、金庫自体が肥大した単一障害点になる**

置き場所はパスワードマネージャー([1PasswordからVaultwardenに移した](/ja/writing/1password-to-vaultwarden/)もの)にした。スマートフォンのアプリは一度ログインすればオフラインのキャッシュが残るので、サーバーが全損してもそこから取り出せる。ただし金庫自身がサーバー上で動いているので、**スマートフォンとサーバーを同時に失うと詰む**。対処は「紙でもう1部持つ」しかない。

## 暗号化と、やらなかったこと

実査したら**事業者側の暗号化(SSE)すら無効**になっていて、写真は生のJPEGのままディスクに置かれていた。「バケットは非公開だから最低限守られている」という感覚は間違いだった。2種類あることを区別しておく。

- **事業者側の暗号化**: 倉庫が金庫に入れてくれるが**鍵は倉庫が持つ**。退役ディスクの流出には効くが事業者自身には無力で、手間はゼロ。🔴 **有効にしても遡らない**
- **送る前に自分で暗号化**: 自分で鍵をかけた箱を渡す。事業者にもアカウント乗っ取りにも強いが、**鍵を失えば永久に読めない**し、既存分は全量を再アップロードになる

やったのは前者を有効化したうえで、**テキスト類・秘密情報・データベースのダンプだけを後者にする**こと。`rclone`には`crypt`という、送信前に暗号化して保存名も不可読にする仕組みがある。初回は6,710オブジェクト・69MBで5分43秒、以後は差分で数十秒だった。

**やらなかったこと**。

- **写真ライブラリ131GBは自分で暗号化していない**。全量の再アップロードになるのと、暗号化する動機(「事業者に読まれたくない」のか「凍結で消えるのが嫌」なのか)を整理できていなかったため。後者ならもう達成済みで、前者ならまだ未達。**整理できていないまま重い工事をしない**
- 🔴 **パスワードの保管庫も、意図的に暗号化していない**。中身はそれ自体がゼロ知識暗号化(サービス側も読めない方式)済みで平文ではなく、何より**暗号化パスワードの保管場所がその金庫なので、暗号化すると循環依存になる**

## 誰も戻したことのないバックアップは、バックアップではない

**1. 生のファイルから実際に復元して突き合わせる。** 124ファイルが完全一致した。暗号化remote経由でちゃんと復号できることも同時に確かめられる。

```bash
rclone copy <暗号化remote>:<対象パス> /tmp/restore-test/
diff -rq /tmp/restore-test/ /home/<user>/<元のディレクトリ>
```

**2. 週次スナップショットを取り出して`tar xzf`で展開する。** 6,644ファイル・74MBが正常に展開でき、自動処理の定義ファイル16本まで含まれていた。

**3. 全ファイルを照合する。** 差分19件。中身を見たら**すべて同期が走った時刻より後に生成されたファイル**で、取りこぼしはゼロだった。

```bash
rclone check --one-way <ローカル> <暗号化remote>:<対象パス>
```

`--one-way`はリモートにしかない古い版を差分に数えないので、検証にはこちらを使う。

併せて**事業者からの通知メールの読み方**を決めた。「マスターキーが生成されました」のような通知は、**自分がコンソールを触っていた日なら本人操作、触っていない日なら本物の警戒シグナル**。先に線引きしないと、通知を全部無視する習慣がつく。

## 残った1系統の弱いところ

- **事業者1社への依存は未対策**。アカウントの凍結や会社都合には何の備えもない。別会社のストレージへ追記専用でもう1本(月€4前後)が答えだが、見送った
- **削除の伝播と容量の兼ね合いが未整理**。送信側の鍵から削除権限を外すと`rclone sync`が使えず`copy`しかできなくなり、ローカルで消したものが残り続けて容量が増える。守りと費用がここで正面衝突する
- **一番大きい穴は、サーバーを乗っ取られた場合**。1系統しかないので、送信に使っている鍵を盗られたらバックアップ本体を消される。これは別テーマとして切り出し、鍵の権限削減・削除が伝播しない複製先・サーバーの外で動く見張りの3層で作り直した。そちらは[バックアップを「消されても戻せる」形にする](/ja/writing/backup-ransomware-resistant/)に書いた

費用は全バックアップ合計125GBで**月約$0.69**。一本化で減ったのは費用ではなく、**気にかけておく仕組みの数**だった。

# 手順

ここから下はClaude（AnthropicのAIアシスタント）が書き、自分の環境で実行して結果を確かめたものだ。

置いておく理由は2つある。ひとつは、**作業の全体像と長さが着手の前に分かる**こと。見てのとおり10段階で、重い工事ではなく「突き合わせ」と「確認」が大半を占める。もうひとつは、**自分が使っているAIに「これと同じことをやりたい」と渡す材料になる**こと。ゼロから説明するより、動いた実例を見せたほうが早い。

道具の版は上がるので、オプション名や設定ファイルの書式は実行前に公式ドキュメントで現在の形を確認してほしい。

## 前提の環境

- 常時起動しているLinuxサーバー1台（自分の場合はUbuntu 24.04のVPS）
- `rclone`（いろいろなクラウドストレージへファイルを同期するコマンド）が入っていて、オブジェクトストレージへの接続設定が1つ済んでいる状態。自分の送り先はBackblaze B2
- `cron`（決めた時刻にコマンドを自動実行する仕組み）が使える状態。**OSのイメージによっては`cron`パッケージ自体が入っていない**ことがあり、無いと`crontab -`が黙って失敗する
- 止めるほうの系統（自分の場合はGitの非公開リポジトリへの日次`push`）が今も動いていること。**止める前に突き合わせるので、動いているうちに始める**

## Step 1: 止める側の中身を、実物から列挙する

設計書や自分のメモではなく、**実際のファイル一覧とスクリプト本文**から出す。

```bash
# 止める側のリポジトリに何が入っているか
git ls-files | awk -F/ '{print $1"/"$2}' | sort -u
du -sh .git
```

- 🔴 **メモの箇条書きだけを読んで判断すると外す。** 自分はここで一度「テキスト類が残す側に入っていない」と誤判断した。同期スクリプトの本文を開いたら既に実装済みだった。**同期スクリプトは必ず本文を開いて読む。**

## Step 2: 残す側の対象リストと突き合わせる

残す側のスクリプトが実際に何を送っているかを、スクリプト本文と送り先の一覧の両方から出す。

```bash
# 送り先に実在するトップレベルの入れ物を見る
rclone lsf --dirs-only <remote名>:<バケット名>/
```

- **容量の大きい入れ物に`rclone size`を掛けると数分かかる**。全体像を見るだけなら`lsf --dirs-only`で足りる。
- 🔴 **`sudo rclone`は`~`を`root`のホームと解釈する**ので、設定ファイルの場所を`--config /home/<user>/.config/rclone/rclone.conf`のように明示する。しないと「設定が見つからない」で空振りする。
- ここで自分は**本物の穴**を見つけた。環境変数をまとめたファイル（`.env`。各種サービスのトークンが入っている）が**どちらの系統にも無かった**。2系統あっても、どちらにも無いものは存在する。

**同時に「分母」も点検する。** ログの「33件すべて成功」は「やると決めた33個は通った」としか言っておらず、**スクリプトに書き忘れたものは永久に静かに落ちる**。見落としを構造的に減らすには3方向から同時に見る。

```bash
docker ps --format '{{.Names}}'          # コンテナで動いているもの
systemctl list-units --type=service      # 常駐サービスで動いているもの
ls /home/<user>                          # データの置き場
```

- 🔴 **片方からだけ見ると、もう片方は構造的に見えない。** 自分の場合、`docker ps`に出ないsystemd側のサービスを数えていなかったため、**常駐サービスの定義ファイル・`crontab`・ファイアウォールのルールが1つもバックアップに入っていなかった**。データは全部戻るのに**どう起動するかが戻らない**状態だった。
- 🔴 **`rclone`はシンボリックリンクを黙ってスキップする**（`Can't follow symlink without -L`）。常駐サービスの定義ディレクトリは中身の多くがリンクなので、`cp -aL <元> <一時ディレクトリ>`で実体化してから送る。これを踏むと「同期した気になって実は空」になる。

## Step 3: Gitの履歴そのものを、ファイルとして退避する

履歴は普通のファイル同期では運べない。`git bundle`（リポジトリ全体を1ファイルに固める機能）を使う。

```bash
git bundle create /tmp/history-<日付>.bundle --all
git bundle verify /tmp/history-<日付>.bundle
rclone copy /tmp/history-<日付>.bundle <暗号化remote>:<保存先>/
```

- 🔴 **`root`で`git`を叩くと`detected dubious ownership`で弾かれる**。ディレクトリの所有者ユーザーで実行する（`sudo -u <user>` など）。
- **履歴に秘密情報が入っている前提で、平文の送り先ではなく暗号化した送り先へ置く**（Step 5）。自分のリポジトリの履歴には、過去に誤って入れたトークン類とサーバーの秘密鍵が残っていた。
- **往復まで確認する。** 取り出して`md5sum`が一致すること、`git clone <bundleファイル> <ディレクトリ>`でコミット数が復元できること、履歴の中にしか無いファイルを`git cat-file -s`で元のサイズどおり取り出せること。自分の場合831MB・162コミットで通った。
- 🔴 **これは一度きりのスナップショットで、以後履歴が伸びても自動では更新されない。**

## Step 4: 止める前に「止める側にしか無いコミット」がゼロだと確認する

```bash
git rev-list --count <リモート名>/main --not --all
```

`0`であること。ローカルが持っていない版がリモートにある状態で止めると、その分が消える。

- **サーバー上から`git fetch`できない環境では、リモートの現況はホスティング側のAPIで確認する**（自分は`gh api`でブランチの先頭を取り、ローカルの値と一致することを見た）。

## Step 5: 送る前に自分で暗号化する経路を1本足す

`rclone`には`crypt`という、送信前に暗号化して保存名も不可読にする仕組みがある。既存の平文の送り先の下に`enc`のような入れ物を1つ作り、そこを指す`crypt`の設定を足す形にした。

```bash
rclone config          # 新しいremoteを追加し、種別に crypt を選ぶ
```

- **対話の項目名と順序は版で変わるので、公式ドキュメントで現在の書式を確認すること。** 確実に押さえるべき点は2つだけ:
  - **パスワードとsalt（2つ目のパスワード）の両方が必要で、片方だけでは復号できない。**
  - **この2つを失うとバックアップは永久に読めない石になる。** 先にStep 9の金庫へ入れてから使い始める。
- **対象の選び方。** 自分はテキスト類・秘密情報・データベースのダンプを`crypt`側にし、写真ライブラリとパスワード管理ソフトのデータは平文のままにした。初回は6,710オブジェクト・69MBで5分43秒、以後は差分で数十秒だった。
- 🔴 **パスワード管理ソフトのデータは意図的に平文のまま残した。** 中身はそれ自体が暗号化済みで、何より**暗号化パスワードの保管場所がその金庫なので、暗号化すると循環依存になる**（鍵を取り出すために金庫を復元し、復元するために鍵が要る）。
- 🔴 **送り先を変える作業は「移す」だけでは終わらない。古い置き場を消すまでが1セット。** 自分は添付ファイルの送り先を平文側から暗号化側へ移したあと古いコピーを消し忘れ、1,589件・1.23GBが二重保管かつ平文のまま残っていた。消す前に`rclone check --one-way`で暗号化側に全件あることと、実ファイルを取り出して復号できることを確かめてから`rclone purge`する。
- **事業者側の暗号化（SSE）も、別物として管理画面で有効にしておく**（Buckets → Bucket Settings → Default Encryption 相当の場所）。🔴 **有効にしても遡らず、以後届くファイルにしか効かない。**

## Step 6: スクリプト本文の平文の秘密を外に出す

データベースのダンプを取る行に管理者パスワードが直書きされていた。権限600のファイルに切り出して読み込む形に変える。

```bash
# スクリプト冒頭
set -uo pipefail
ENVFILE=/root/backup-scripts/.env      # 600 / root:root
[ -r "$ENVFILE" ] || exit 1
set -a; . "$ENVFILE"; set +a
: "${DB_ROOT_PASSWORD:?未設定}"
```

- **渡し方はコマンドライン引数ではなく環境変数経由にする。** `-p'…'`のような引数は`ps`で他のユーザーから見えてしまう。`docker exec -i -e MYSQL_PWD="$DB_ROOT_PASSWORD" …` / `-e PGPASSWORD="$…"` の形に揃えた。
- **変数が空なら`: "${VAR:?未設定}"`で止める。** 黙って空のパスワードで走らせないため。
- 🔴 **平文の秘密はスクリプト本文を直しても消えない。** 自分の場合、過去の退避ファイル（`.bak`）5本・稼働中のコンテナの環境変数・新設した`.env`に同じ値が残っていた。**本当に消すにはパスワードの変更が必要。** 変更する場合は①データベース側で`ALTER USER`を先に打つ ②読み込むファイルを新値にする ③コンテナの定義を新値にする ④コンテナを作り直す（環境変数は再作成しないと更新されない）⑤バックアップを手動実行して完走を確認する ⑥古い退避ファイルを`shred -u`、の順序を守る。**①を飛ばすとバックアップのダンプが静かに失敗する。**
- 🔴 **バックアップを取る道具自体がバックアップ対象外になりやすい。** 同期スクリプトを置いたディレクトリ（自分は`/root/backup-scripts`）はどちらの系統にも入っていなかった。1行足して暗号化側へ送る。

```bash
step "backup-scripts"  $RC sync /root/backup-scripts "${ENC}backup-scripts" --exclude "*.log"
```

（`$RC`は`rclone`の呼び出し、`${ENC}`は暗号化した送り先を指す変数で、どちらも自分のスクリプトで既に定義済みのもの）

- **既存の行の書き方を真似る形で足すと、変数名や送り先の指定を推測せずに済む。** これは効いたので毎回そうしている。編集後は`bash -n <スクリプト>`で文法を見てから手動実行する。

## Step 7: 途中で失敗しても「どこまで通ったか」が残る形にする

- 🔴 **`set -e`だけで組むと、途中で止まったときに何も分からない。** 自分の旧スクリプトは最後の処理で`sudo`がパスワードを求めて止まり、**34回の起動のうち完走は5回**だった。データ本体の各工程は成功していたので実害は無かったが、「完走しました」のマーカーが1ヶ月出ていないことに気づけなかった。
- 直した形は、各処理を`step "名前" <コマンド…>`という関数で包んでOK/FAILを個別にログへ出し、最後に`=== Backup finished OK ===`または`=== Backup finished WITH FAILURES ===`のどちらかを必ず出す構造。**完走マーカーを1行にしておくと、監視する対象がそれ1つになる。**
- **`sudo`に依存する処理はスクリプトから外す。** 対話的なパスワード要求は自動実行では必ず詰まる。
- 🔴 **`timeout`付きの`ssh`で長時間のスクリプトを走らせると`ssh`が先に死ぬ**（終了コード137）が、**サーバー側のスクリプトは完走している**。ログを見るまで「途中で止まった」と判断してはいけない。

## Step 8: 浮いた分を、別の軸に回す

1系統になったぶんを「頻度」と「保持期間」に回した。

```cron
30 2 * * *          /root/backup-scripts/backup-to-b2.sh         # 全体を1日1回
0 5,11,17,23 * * *  /root/backup-scripts/backup-workspace-text.sh # テキスト類だけ1日4回
```

- テキスト類だけを対象にした軽い同期にしたので約10秒で完走する（重い写真ライブラリに触らない）。これで**RPO（障害時に失われる最大の時間幅）が最大24時間から最大6時間に縮んだ**。
- 加えて、30日を超える長期の記録として**テキスト類のみの日付付き`tar.gz`スナップショットを週1回**置いた。対象は会話ログ・設定・スキル定義・添付を除いたデータ・画像を除いた生成物で、**実測16MB**。年0.8GBなので費用はほぼゼロ。
- 送り先のバージョン保持（上書き・削除された古い版を一定期間取っておく設定）を確認しておく。自分の入れ物は**旧バージョンを30日保持**で、実際にデータベースのダンプは26世代遡れた。**30日の「取り消し」が成立していれば、Gitの履歴機能の大部分は代替できる**という判断の根拠がここ。

## Step 9: 復元テストを3通りやる

誰も戻したことのないバックアップはバックアップではない。**止めてからではなく、止める前にやる。**

**1. 生のファイルから実際に復元して突き合わせる。**

```bash
rclone copy <暗号化remote>:<対象パス> /tmp/restore-test/
diff -rq /tmp/restore-test/ /home/<user>/<元のディレクトリ>
```

自分の場合124ファイルが完全一致した。暗号化経路でちゃんと復号できることも同時に確かめられる。**復元には`copy`を使い`sync`は使わない**（`sync`は空ディレクトリを消し、過去に別のサービスで障害化した実績がある）。

**2. 週次スナップショットを取り出して展開する。**

```bash
rclone copy <暗号化remote>:<保存先>/<スナップショット名>.tar.gz /tmp/
tar xzf /tmp/<スナップショット名>.tar.gz -C /tmp/snap-test/
```

6,644ファイル・74MBが正常に展開でき、自動処理の定義ファイル16本まで含まれていた。

**3. 全ファイルを照合する。**

```bash
rclone check --one-way <ローカル> <暗号化remote>:<対象パス>
```

`--one-way`はリモートにしかない古い版を差分に数えないので、検証にはこちらを使う。自分の結果は差分19件で、中身を見たら**すべて同期が走った時刻より後に生成されたファイル**。取りこぼしはゼロだった。

**4. 鍵の経路も検証する。** 「サーバーも手元も同時に失った」局面から復元できるかは、**金庫のメモに書かれた値だけで送り先が見えるか**を試さないと分からない。自分はこれをスクリプトにして、鍵を差し替えるたびに回すようにした。

## Step 10: 再発行できない鍵だけ金庫に入れる

**バックアップを復元するための鍵が、バックアップの中にしか無いと、永久に開かない。** 入れるものと入れないものを先に線引きする。

- **入れる（再発行不能）**: `crypt`の暗号化パスワードとsalt、ストレージ事業者のアカウントの2段階認証バックアップコード、復元用の接続情報（`rclone`の設定ファイルの中身）
- **入れない（再発行可能）**: 各種APIトークン、ストレージのアプリケーションキー。上位のアカウントにログインできれば1分で作り直せる
- 🔴 **何でも放り込むと、金庫自体が肥大した単一障害点になる。**
- 置き場所をパスワードマネージャーにする場合、**スマートフォンのアプリは一度ログインすればオフラインのキャッシュが残る**ので、サーバーが全損してもそこから取り出せる。ただし金庫自身がそのサーバー上で動いているなら、**スマートフォンとサーバーを同時に失うと詰む**。対処は「紙でもう1部持つ」。
- 🔴 **鍵をチャットやターミナルの貼り付けで露出させないこと。** 自分は作業中にマスクを書き損じて、データベースのパスワードをツール出力に出してしまった。しかもその会話ログは毎晩バックアップに入るので、**平文が送り先のバージョン履歴に数日分載った**。マスクはあとから遡れない。鍵の状態を確認したいだけなら、本体を出さないコマンド（キーの一覧と権限だけを出すもの、設定ファイルのセクション名だけを出す`grep "^\[" <ファイル>`など）を使う。
