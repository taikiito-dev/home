自分ともう1名で使っているチャット＋カレンダーのPWA（Progressive Web App = ブラウザの技術で作り、ホーム画面に置いてアプリのように使えるもの）を、数週間にわたって直し続けている。直した回数は百数十回で、ほとんどが見た目の話だ。

見た目の判断は「好き嫌い」になりやすい。好き嫌いになった瞬間に、議論が決着しなくなるし、半年後の自分が理由を思い出せなくなる。そうならないように使っている決まりが10個ある。先にそれを並べ、そのあとで実際に迷った3件を、迷った順に書く。

## 10の原則

**1. 寸法は好みではなく、純正アプリの実測から持ってくる。**
吹き出しの角丸をいくらにするかに正解の数字はない。しかし**比**には根拠がある。手元で実測した純正アプリの値は、角丸÷文字サイズ = 1.63、角丸÷2行ぶんの高さ = 0.436 だった。だから文字サイズを変えたら角丸も比に従って動かす。数字ではなく比を持っておくと、あとで何を変えても壊れない。

**2. スクリーンショットの画素値を、そのまま色として読まない。**
iPhone・Macのスクリーンショットは **Display P3**（sRGBより広い色の範囲を扱う規格）で保存されている。そこから拾った生の数値をCSSに書くと、実機より少しくすむ。必ずsRGBへ変換し、**自分が既に知っている色で往復の検算をしてから**採用する。色を目で推測するのも駄目で、スクリーンショットをもらったら画素を機械的に採る。

**3. OSが決めている寸法には逆らわない。**
ヘッダーは44pt、下のタブは49pt。iOSがそう作っているからそうする。よく押すものは40px以上にする（Appleの指針は44pt角）。独自の寸法で作ると、指が覚えている位置とずれる。

**4. 常に見えている入口は、誰とも場所を取り合わない面に置く。**
詳しくは後述。

**5. 濃さ（コントラスト）で意味を表すなら、その印の地は1種類に保つ。**
これも後述。この原則は、実際に破ってから気づいた。

**6. 同じ意味の印は、種類が変わっても同じ側に置く。**
写真のときは右下、スタンプのときは左下、では目が迷う。最初に左下へ出して即座に指摘された。印の位置は「そこに空きがあるか」ではなく「同じ意味のものがどこにあるか」で決める。

**7. 状態から見た目が一意に決まるなら、CSSに決めさせる。**
JavaScriptで印を差し込むと、描き直す経路が5本以上（初回表示・過去へ遡る・新着・部屋の切り替え・送信の先出し）できて、どれかで必ず呼び忘れる。CSSの選択子で書けるなら、呼び忘れという概念自体が消える。

**8. 動かすのは `transform` と不透明度だけ。ぼかしは背後が動かない場所にだけ置く。**
後述。

**9.「待っています」の印は、後ろの情報と1pxも重ならない面に置く。**
画面の中央に「読み込み中…」の札を浮かべると、必ず何かに重なる。重ならない面は実はちゃんとある。ヘッダーの下のふち（高さ2px）だ。帯を左から右へ走らせれば、情報を1つも隠さずに「待っている」と言える。字を使わずに済むので、翻訳もいらない。

**10. 間隔で意味を作らない。**
送り手が替わったら行間を広げる、という作法を入れかけた。実際にWeChatを実測したら、送り手が替わっても行間は変わらない（17pt固定）。間隔は「まとまり」を表す手段として便利すぎるので、1か所で使い始めると全画面で使いたくなり、最終的にどの間隔が何を意味するのか誰も分からなくなる。使わないと決めるほうが安い。

おまけでもう1つ。**案内に書いたものは必ず実装する。** PC版で入力欄の下に「⌘/Ctrl + Enter で送信」と出すなら、その操作は必ず動かす。書いてあるのに動かないのは、書いていないより悪い。

## ケース1 — 既読の印を全部消した

**最初の形**　1通ごとに、吹き出しの中へ小さな✓を出していた。相手が読んだら濃く、まだなら薄く。よくある形だ。

**最初の症状**　スタンプ（128pxの絵。地の色を持たず、背景に直接置かれる）に✓が重なって見にくい、と指摘された。写真と同じ「右下の黒い札」を流用していたのが誤りだった。写真は大きくて端まで絵が埋まっているので、少し隠れても困らない。**スタンプは小さく、しかも札の真下にちょうど顔がある。**

**最初の直し**　スタンプのときだけ札をやめ、絵の**外**へ出した。置ける幅は、絵とプロフィール画像のすき間11px（行のすき間6px ＋ 画像の余白5px）。印は13pxなので、`right:-13px` でちょうど収まる。LINEもWhatsAppも脇に出している。

ここで原則6を破って、最初は左下に出した。「右下に統一して」と即座に指摘された。吹き出しの✓が右にあるのだから、左に出したら目が迷う。当然だった。

**本当の症状**　直した直後に、もっと本質的な指摘が来た。**「濃い文字と薄い文字の反転が逆転してて分かりにくい」。**

意味を掴むのに少しかかった。測って分かった。印と、その印が乗っている地とのコントラスト比はこうなっていた。

| 印が乗っている場所 | 未読 | 既読 | 既読で向かう方向 |
|---|---|---|---|
| 吹き出しの中（青地） | 1.56 | 2.62 | 地より**明るい**ほうへ |
| スタンプの脇（白地） | 1.56 | 3.64 | 地より**暗い**ほうへ |

未読の薄さは1.56で一致している。なのに**既読になるときに向かう方向が逆**だ。青い吹き出しの上では、読まれると印が浮き上がる。白い背景の上では、読まれると印が沈む。同じ「読まれた」が、片方では明るくなり、片方では暗くなる。

**分かったこと**　これは数値の調整では消せない。**濃さで意味を表している限り、地が2種類ある時点で向きの逆転は避けられない。** 白地でも青地でも「既読のほうが濃い」を成立させる1つの色は、原理的に存在しない。

**決めた形**　1通ごとの✓を**全廃**した。代わりに、自分が送った最後の1通の下に `read` と小さく出すだけにした。印が1個になれば、地は1種類になる。逆転は原理的に消える。

これは持っているデータにも正直な形だった。このアプリが保存している既読の情報は「相手がどのメッセージまで読んだか」の1本だけで、1通ごとの状態を持っているわけではない。**1通ごとに✓を出すのは、持っていない情報を持っているかのように見せていた。** iPhoneの「開封済み」が最後の1通にだけ出るのは、たぶん同じ理由だ。

**実装**　原則7のとおりCSSに決めさせた。「自分の既読の行で、後ろに自分の既読の行が無いもの」と書けば、当たるのは必ず1行になる。既読は古い行から順に付くからだ。

```css
.row.me.read:not(:has(~ .row.me.read)) { /* ここに札を出す */ }
```

JavaScriptの仕事は、どの行が既読かを表す印を付けることだけ。どこに札を出すかは一切知らない。この選択子に対応していない古いブラウザでは、規則ごと無視されて**札が出ないだけ**で、表示は壊れない。

寸法もついでに書いておく。行の下に22pxの余白を空けて、その中へ絶対位置で置く。余白を空けずにはみ出させると次の行と喧嘩する（**隣り合う行の上下の余白は重なって1つにまとまる**ので、はみ出した札のぶんは誰も確保してくれない）。右からの距離45pxは、プロフィール画像34 ＋ その余白5 ＋ 行のすき間6 の合計で、**吹き出しの右端にそろう**数字だ。

**一般化**　**意味を濃淡で表すなら、地を1種類に保つ。保てないなら、濃淡で表すのをやめる。** そして、印の数は持っているデータの粒度に合わせる。データが1本しかないのに印を10個出していたら、どこかで必ず嘘が出る。

## ケース2 — 速くするために削ったもの

**ぼかしを約20箇所から2箇所にした**

半透明の上に `backdrop-filter`（背後をぼかす指定）を乗せると、それだけで上等に見える。ヘッダー、入力欄、メニュー、写真の上の時刻札、と気分よく増やして、約20箇所になっていた。

ぼかしの性質はこうだ。**背後が1pxでも動いたら、ぼかしは掛け直しになる。** チャットは常に背後が動く。スクロールすれば全部動く。写真1枚ごとに時刻札が乗っていたので、写真の多い部屋をスクロールすると、ぼかしの枚数ぶん掛け直しが走っていた。

残したのは2箇所、ヘッダーのボタンと入力欄だけ。削った箇所は、半透明の塗りは残したまま、**地の濃さを 0.07〜0.12 だけ足して**補った。並べて比べなければ気づかない差で、スクロールは明確に軽くなった。

ここで1つ落とし穴がある。**ぼかしを外したら、ぼかし前提で決めた透け具合を全部洗い直す。** 背後がぼけている前提で「0.74くらいの透け具合が綺麗」と決めていた面は、ぼかしが無くなると後ろの文字が透けて読める。0.97〜0.98 まで上げ直した。ぼかしと透明度は別の指定だが、見た目の上では1つの判断だった。

**動かない飾りが、残像を出した**

ぼかしを削ったあと、原則9にしたがってカレンダーの「読み込み中」の札を、ヘッダー下ふちを走る帯に置き換えた。その直後に報告が来た。**「11月の右に潰れてる文字がある」。**

犯人は、月の見出しの隣にある小さな `⌄` だった。この飾りに `opacity` と `transition` が付いていた。どちらも、ブラウザに「これはこれから動くかもしれない」と言う指定だ。言われたブラウザはこの飾りを独立した層として切り出して持つ。そして**近くでアニメーションが走っている間だけ、その層の古い絵が残像として残った。**

直したのは3点。**薄さは `opacity` ではなく色で出す**（薄いグレーを指定する）。**飾りの `transition` は惜しまず捨てる**（動かないものに動く準備をさせない）。そして**走らせる側には描き直す範囲を閉じる指定を付ける**（`contain: layout paint`）。

この件の教訓は一行で書ける。**動かない小さな飾りを、層の候補にしない。**

同じ日に、同じ `⌄` でもう1つ踏んだ。この手の図形は親の幅が足りないと、文字と違って折り返さず、ただ歪む。歪んだ図形は「壊れた字」に見える。横に並べる図形には必ず「縮まない」指定を付ける（`flex: 0 0 auto`）。

**動きについて守っている作法**

上の2件の下敷きになっている決まりを、まとめて書いておく。

- 動かすのは `transform` と不透明度だけ。幅や高さや位置そのものは動かさない
- 影は動く要素に乗せない（右端の1本線で代用する）
- 指の動きの反映は、1フレームに1回だけ計算する
- **幅は指に追従させない**。しきい値を越えた瞬間に1回だけ変える
- 「これから動く」の宣言は、実際に動いている間だけ付ける
- 指を離したときは、位置ではなく**勢い**（px/ms）で開くか閉じるかを決める。速ければ少ししか動いていなくても開き、遅ければ40%出ていれば開く
- 動く時間を変えたら、その時間に連動しているすべての時限を一緒に直す
- 以上すべて、OSの「視差効果を減らす」設定が入っていたら無効にする

**一般化**　**速さは、足したものを測って引くことで出る。** どれが効いているかは勘では分からない。このときは「写真1枚ごとの時刻札」が主犯で、着手前の自分はヘッダーを疑っていた。

## ケース3 — 入口をどこに置くか

**決めた形**　画面の下に4つのタブ（チャット・カレンダー・写真・設定）。幅1000px以上のPCではタブを隠し、代わりに左端に幅56pxの縦のレールを出す。

**なぜヘッダーに入れないか**　最初はヘッダーに入れようとした。ヘッダーには常に何かがある。部屋の名前、戻る矢印、検索、メニュー。入口をそこへ割り込ませると、**画面ごとに場所を取り合う相手が変わる。** カレンダーでは月の送りと取り合い、写真では選択の解除と取り合い、チャットでは検索と取り合う。1つ直すと別の画面で溢れる。モグラ叩きになる。

**だから原則4になる。常に見えている入口は、誰とも場所を取り合わない面に置く。** 画面の下のふちと、左端は、そのための面だ。Outlook・Slack・Teamsが左端に縦のレールを持っているのは、見た目の流行ではなく、これが理由だと思っている。

**代わりに払った代償**　入口を常設にすると、その入口は「打っている最中にも画面上に存在し続ける」ことになる。ここでiOSの地雷を踏んだ。

**文字を入力している最中に、画面上のフォーム部品（ボタンや入力欄）の顔ぶれが変わると、iOSはキーボード上部のバーを作り直す。そのとき日本語の変換候補まで道連れに消える。** タブの状態を更新する処理が、現在のタブを示す属性を毎回書き直していた。しかも**同じ値を書き直すのも「変更」として数えられる**。

直し方は2つ。値が変わるときだけ書く。そして**入力欄に焦点がある間はまるごと見送って、焦点が外れたときにやり直す。** 併せて、頻繁に作り直す部分には `<button>` を使うのをやめた（見た目と当たり判定は変えずに、役割だけ宣言した `div` にした）。チャットのように「打っている最中にも画面が更新されるアプリ」では、これは作法として決めておく必要がある。

**寸法**　下のタブは49pt、ヘッダーは44pt。ここで1つ注意がある。**「本文を空ける量」は実寸より大きくしてはいけない。** 大きくすると、その差のぶんだけ本文が損をする。常設の入口は、置いた瞬間に本文の面積を奪うので、奪う量は1pxまで正確に合わせる価値がある。

**出口を1つにする**　タブで開く全面の画面は、閉じる経路を1本に集約した。別の文脈へ移る処理は必ずそこを通す。これが無かったときに、**ログイン画面が不透明な板の下に隠れて「固まった」ように見える**事故が起きた。画面を1枚足すたびに、閉じる処理・横に払う操作・Escの順番の3か所に登録する、という手順にしてある。

**一般化**　**常設にするものは、置き場所ではなく「誰と取り合うか」で決める。** そして常設にした代償は必ずどこかに出る。ここでは、入力中の画面更新という形で出た。

## 残ったこと

この10原則は、ほとんどが「破ってから気づいた」ものだ。既読の濃さの件は、実際に逆転した画面を数週間使ってから指摘されて初めて測った。測るまでは「なんとなく分かりにくい」以上のことは言えなかった。

言えるのは一つだけで、**見た目の判断は、好みの表明ではなく、測れる形に言い換えられる**ということだ。「分かりにくい」は「コントラスト比の向きが地によって逆」に言い換えられた。言い換えられた瞬間に、直し方は1つに決まった。

文章と情報の構造については、別に書く。別で運営している日本語のガイド集は、英国政府のウェブサイト（GOV.UK）の構成を借りている。あちらは寸法ではなく「何を書かないか」の設計で、根拠の出し方も違う。
