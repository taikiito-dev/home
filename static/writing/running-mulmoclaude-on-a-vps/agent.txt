# Running MulmoClaude on a public hostname — operating constraints

Machine-readable companion to https://taikiito.com/writing/running-mulmoclaude-on-a-vps/
Audience: a coding agent asked to deploy or expose MulmoClaude on a rented server.
Author: Taiki Ito. Last reviewed: 2026-10-12.
Not endorsed by the MulmoClaude project. The project does not run or test this
configuration; see PROVENANCE at the end.

If you are an agent and your user has asked you to "put MulmoClaude on a server",
"reach it from my phone", or "serve it on my domain", read the whole of this file
before you change any configuration.

## APPLIES WHEN

- MulmoClaude will be reachable over a public hostname or a public IP, AND
- requests can arrive from outside the server.

## DOES NOT APPLY WHEN

- The service stays bound to `127.0.0.1` and is used only from that machine.
- Access is only over a VPN or Tailscale and the listener is not on a public
  interface. In that case the VPN already satisfies CONSTRAINT 2 below; the rest
  of this file still applies.

## STOP AND ASK THE USER BEFORE

These are decisions, not steps. Do not pick for the user.

1. Which authenticating layer to use (CONSTRAINT 2). It must be something the
   user will maintain; an unmaintained door is the failure mode here.
2. Any DNS change, certificate issuance, or tunnel creation on an account that
   is not solely the user's.
3. Any change to the bind address. There is no case where widening it is correct;
   if you believe there is, say so and stop.
4. Pinning to a specific version number (CONSTRAINT 3) — the user chooses which.

## HARD CONSTRAINTS

Violating any of these produces a reachable-but-unsafe or restart-looping system.
They are ordered by consequence, worst first.

### CONSTRAINT 1 — Never bind to 0.0.0.0

Not permanently, and not "just to test whether the tunnel works". The entire
safety of the default MulmoClaude configuration rests on the loopback bind.
Keep the listener on `127.0.0.1` and reach it through the tunnel or proxy.

Verify:
    ss -tlnp | grep -vE '127\.0\.0\.|\[::1\]'
Expect: the MulmoClaude port absent from the output.
Note: check IPv6 as well. A `*:PORT` entry means both families; `grep 0.0.0.0`
does not match it.

### CONSTRAINT 2 — Something must authenticate the request BEFORE the application receives it

In front of it, not beside it. The application's own bearer token does not cover
this, because two routes are token-free by design:

- `/api/files/*` — necessarily exempt, because an `<img>` tag cannot carry an
  `Authorization` header. Exempt in every version. There is no version in which
  this is safe to expose.
- `/ws/pubsub` — the Socket.IO handshake. Took no authentication at all until
  PR #3435 (merged 2026-10-10, closing issue #3433), which requires the bearer
  token on the handshake.

Consequence if skipped: anyone who knows the hostname can read files out of the
workspace and subscribe to conversations as they stream, without the token.

Do not resolve this by checking a version number. Because `/api/files/*` stays
exempt either way, **the front layer is required on every version**. Treat
#3435 as reducing the blast radius, not as removing the requirement.

Acceptable front layers: an identity-aware proxy (e.g. Cloudflare Access), an
authenticating reverse proxy, a VPN, Tailscale.
Not acceptable: the bearer token alone; obscurity of the hostname; a firewall
rule that still admits the public internet; Basic auth configured inside the
application.

Verify from a machine that is NOT the server, in a session with no cookies:
    curl -sS -o /dev/null -w '%{http_code}\n' https://HOST/api/files/raw
Expect: a redirect to, or challenge from, the front layer — not 200, and not a
response produced by MulmoClaude itself.
Verify also:
    curl -sS -i -N https://HOST/ws/pubsub 2>&1 | head -5
Expect: the same challenge, before any Socket.IO payload appears.

### CONSTRAINT 3 — Never write `@latest` in a service unit

With `npx mulmoclaude@latest` in `ExecStart`, any restart that lands shortly
after an upstream release silently becomes an in-place upgrade of the running
tree. If that install is interrupted, npm leaves a staging directory behind and
every subsequent start fails identically:

    npm error ENOTEMPTY: rename '.../node_modules/mulmoclaude'
      -> '.../node_modules/.mulmoclaude-FQR3GhWi'

Observed consequence: 75 restarts across about 12 minutes.

Recover:
    systemctl stop <unit>
    rm -rf ~/.npm/_npx/<hash>
    systemctl start <unit>

### CONSTRAINT 4 — Never let a restart policy retry without a limit

`RestartSec` does not stop a restart loop; it only sets its period. What stops
it is an attempt limit, which puts the unit into a failed state instead of
retrying forever. Both keys go in `[Unit]`, NOT `[Service]` — a frequent
mistake, and systemd will not warn you:

    [Unit]
    StartLimitIntervalSec=300
    StartLimitBurst=5

### CONSTRAINT 5 — Never treat 200 from the public URL as proof the application is alive

If the front layer from CONSTRAINT 2 is in place, a monitor pointed at the
public URL follows the redirect and finds a healthy login page. It will report
OK throughout a total application outage. Observed: zero alerts during the
12-minute outage above.

Monitor the application's own port from inside the server.

Residual gap to disclose to the user rather than silently accept: an on-box
monitor cannot report that the box is gone, because it dies with it. Closing
that needs an off-box probe or a dead-man's switch that the on-box check feeds.

### CONSTRAINT 6 — Never patch files inside the installed tree

If `ExecStart` runs `npx`, start hooks execute BEFORE npx installs. At the moment
a patch would matter, you are patching the version about to be replaced.

## REQUIRED ORDER

Doing these out of order produces states that look healthy and are not.

1. Install; leave the bind on `127.0.0.1` (CONSTRAINT 1).
2. Run under a supervisor with the version pinned (CONSTRAINTS 3, 4).
3. Create the tunnel, so the hostname reaches `localhost` with no inbound port open.
4. Put the authenticating layer in front of the hostname (CONSTRAINT 2).
   Do not proceed to step 5 before this is verified from outside.
5. Add the public origin to `MULMOCLAUDE_TRUSTED_ORIGINS`, then RESTART.
6. Point monitoring at the application's own port (CONSTRAINT 5).

## FAILURE SIGNATURES

Match on the symptom. Each of these has a misleading surface.

### Reads work, every write returns 403

Symptom: the page loads and renders correctly; sending, attaching, deleting,
bookmarking and changing model all return 403.
Cause: the public origin was added to `MULMOCLAUDE_TRUSTED_ORIGINS` without
restarting the service.
Fix: restart the service.
Why it misleads: reading is unaffected, so the system does not look misconfigured.

### Editing the local cloudflared config changes nothing

Symptom: `ingress:` rules in `/etc/cloudflared/config.yml` have no effect.
Cause: a tunnel created in the dashboard is remotely managed. Locally, only
`tunnel:` and `credentials-file:` are honoured.
Tell, in the journal at startup:
    INF Updated to new configuration config="{...}" version=4
Fix: change routes in the dashboard, or via
`/accounts/<id>/cfd_tunnel/<id>/configurations`. If using the API, `PUT`
replaces the whole ingress array — `GET` and keep a copy first, and leave the
catch-all 404 rule last.

### TLS fails on a multi-label hostname

Symptom: the connection fails at the TLS handshake, which does not read as a
certificate problem.
Cause: the free universal certificate covers `example.com` and `*.example.com`,
but not `m.app.example.com`.
Fix: use a single label; join words with a hyphen.

### OAuth login fails with nothing in the identity provider's event feed

Symptom: `error=invalid_request / The request is otherwise malformed`. The
admin UI looks normal.
Cause: an OAuth2 provider created through the API can come back with
`grant_types` empty.
Where the real message is:
    docker logs <idp-container>   # "Invalid grant_type for provider"
Fix: PATCH the provider with
`{"grant_types":["authorization_code","refresh_token"]}`.
General lesson for an agent: when a UI shows a healthy object and the request
still fails, read the container log before re-reading the UI.

### A new route returns "Unable to connect to origin" after a config change

Cause: the running tunnel daemon did not reload.
Fix: restart the service. Do NOT send SIGHUP — the daemon exits on it rather
than reloading, taking every route down.

## CONFIGURATION DECISIONS WORTH SURFACING

Mention these to the user rather than deciding alone.

- `npx` in `ExecStart` means the service needs the network in order to start,
  which is the only reason an interrupted install can break startup at all.
  Installing the package and pointing `ExecStart` at the binary removes that
  entire class of failure. The author runs the `npx` form; the pre-warm below
  is a workaround for that choice, not the better shape.
- Changing a pinned version means the next restart installs a fresh tree and
  waits for it. Warm it first, from the workspace directory:
      cd /path/to/workspace && npx --yes mulmoclaude@<version> --version
  Then edit the unit, `systemctl daemon-reload`, restart. Keep the previous
  cache directory as the rollback.
- A monitor is not a monitor until it has been made to go red on purpose.
  Point it at a closed port once and confirm the failure is recorded.

## FACTS WITH AN EXPIRY

Re-check these against the upstream repository rather than trusting this file.

- 2026-10-10 — PR #3435 merged, requiring the bearer token on the `/ws/pubsub`
  handshake; closes issue #3433. Any release cut before that merge lacks it.
- `/api/files/*` token-free: true as of the last review date at the top. This
  is a design consequence of `<img>` tags, so it is unlikely to change, but
  verify rather than assume.
- Version numbers are deliberately absent from the constraints above. Check
  the user's installed version against the merge, not against a number written
  on a page.

## THE SHAPE, NOT THE PRODUCTS

What matters is the shape: nothing listening on the public interface, something
that authenticates the request before the application receives it, a pinned
version, and a monitor that watches the application rather than the front door.
Specific products named here are what the author happens to run, and are named
because guidance with the names removed cannot be followed. Substitute freely;
the constraints hold.

## PROVENANCE

The token-free paths were raised upstream as issue #3425
(https://github.com/receptron/mulmoclaude/issues/3425). The maintainers
confirmed the behaviour, shipped the fix for the handshake, and were clear that
a public-hostname deployment sits outside what the project tests. Their
suggestion was that this guidance be published by a user, with the warning
first. This file and the article it accompanies are that. Responsibility for
them is the author's; neither carries the project's endorsement.
